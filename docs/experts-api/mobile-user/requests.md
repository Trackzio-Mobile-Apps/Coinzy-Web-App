# Mobile User — Requests

All endpoints in this section require **mobile-user JWT** authentication via `Authorization: Bearer <external-jwt>`.

---

## Upload Request Media

### `POST /users/uploads`

Uploads one or more files and returns public URLs that can later be submitted in `payload.media`.

Intended flow: upload the coin files first, read the returned `data.urls`, then send those URLs in `payload.media` when creating the request.

- Auth: mobile-user JWT
- Form field: `files`
- Count: 1-7 files by default, configurable with `UPLOAD_MAX_FILES`
- Images: JPEG, PNG, or WebP, limited by `UPLOAD_MAX_IMAGE_BYTES`
- Videos: MP4 or MOV, limited by `UPLOAD_MAX_VIDEO_BYTES`
- Storage requires `AWS_REGION`, `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `S3_BUCKET`, and `MEDIA_PUBLIC_BASE_URL`
- Public bucket/CDN policy is configured outside the API, in AWS

**Success:** `201`
```json
{
  "error": false,
  "message": null,
  "data": {
    "urls": [
      "https://media.example.com/coinzy/uploads/2026-07-15/uuid-obverse.jpg"
    ]
  }
}
```

**Errors:** `400` invalid files or limits, `503` upload config missing, `502` S3 storage failure

## Create Request

### `POST /users/requests`

Creates a new expert request, spending one credit.

**Optional header:**

- `x-fcm-token: <firebase-device-token>` stores a transient request-scoped
  token used for best-effort mobile-user request lifecycle notifications

**Request body:**

```json
{
  "country": "IN",
  "payload": {
    "media": {
      "obverse": ["https://media.example.com/coinzy/uploads/obverse.jpg"],
      "reverse": ["https://media.example.com/coinzy/uploads/reverse.jpg"],
      "edge": ["https://media.example.com/coinzy/uploads/edge.jpg"],
      "video": null
    }
  }
}
```

- `country` is required, normalized to uppercase, and must be one of the allowed values configured via `ALLOWED_COUNTRIES` (pipe-separated)
- `payload` defaults to `{}`
- `payload.media` is optional. When present, it must contain only `obverse`, `reverse`, `edge`, and `video`.
- For media-backed requests, call `POST /users/uploads` first and pass the returned URLs into `payload.media`; request creation does not accept multipart files directly.
- `obverse`, `reverse`, and `edge` must each contain 1-2 HTTPS URLs
- `video` must be one HTTPS URL, or `null`
- Any HTTPS host is accepted
- invalid `payload.media` is rejected before credit is spent
- `displayId` is generated by the backend for display only. Mobile routes, searches, relations, and integrations must continue to use the MongoDB `_id`.
- `coinTitle` is `null` while the evaluation is pending. The assigned expert supplies it when submitting the completed report, so clients can display a neutral fallback such as `Coin Evaluation` until then.
- The request deadline is set when the request is created using `REQUEST_DEADLINE_HOURS`. Accepting an offer does **not** extend or reset that deadline, so later acceptance leaves less remaining work time.
- If any post-spend step (create, allocation, job scheduling) fails, the spent credit and partial request records are rolled back before returning the error

**Success:** `201`
```json
{
  "error": false,
  "message": null,
  "data": {
    "request": {
      "_id": "507f1f77bcf86cd799439077",
      "displayId": "EV-7K3P9Q2A",
      "coinTitle": null,
      "country": "IN",
      "payload": {
        "media": {
          "obverse": ["https://media.example.com/coinzy/uploads/obverse.jpg"],
          "reverse": ["https://media.example.com/coinzy/uploads/reverse.jpg"],
          "edge": ["https://media.example.com/coinzy/uploads/edge.jpg"],
          "video": null
        }
      },
      "status": "offered",
      "assignedExpertId": null,
      "reportId": null,
      "deadlineAt": "2026-06-25T00:00:00.000Z",
      "acceptedAt": null,
      "submittedAt": null,
      "completedAt": null,
      "createdAt": "2026-06-22T00:00:00.000Z",
      "updatedAt": "2026-06-22T00:00:00.000Z"
    },
    "creditBalance": 9
  }
}
```

The response does not expose the stored FCM token, credit-ledger linkage, internal-expert linkage, previous-expert history, or allocation bookkeeping.

**Errors:** `400` invalid body or insufficient credits

## List My Requests

### `GET /users/requests`

Returns only requests owned by the authenticated user.

Requests use the same mobile-safe shape shown under `POST /users/requests`, newest first. `displayId` may be `null` only for legacy rows created before display IDs were introduced.

Request objects also include nullable `reportId`. It remains `null` until the request is completed and the report is submitted.

Clients derive presentation values such as `In Progress`, progress-step labels, and remaining hours from `status`, `deadlineAt`, and the lifecycle timestamps. Those UI labels and countdowns are not stored fields.

**Success:**
```json
{ "error": false, "data": { "requests": [] } }
```

## Get Request By ID

### `GET /users/requests/:id`

Returns a single request owned by the authenticated user.

The `:id` route parameter is always the MongoDB `_id`, never `displayId`.

**Success:**
```json
{ "error": false, "data": { "request": {} } }
```

**Errors:** `404` request not found

## Retry Request

### `POST /users/requests/:id/retry`

Restarts a deadline-missed request with a fresh allocation cycle.

- Body: none
- Optional header: `x-fcm-token: <firebase-device-token>` refreshes the stored
  token for that same request; when omitted, the existing request token stays as
  is
- Only allowed while the request is `deadline_missed`

**Behaviour:**
- Preserves `previousExpertIds`, resets lifecycle timestamps, starts fresh allocation, and schedules fresh jobs
- The new deadline is recalculated when the retry starts. It is not anchored to the later expert acceptance time.
- Closes only still-open offer rows from the missed attempt. Because `RequestOffer` is unique on `{ requestId, expertId }`, selected experts may have their existing rows reactivated with fresh `OFFERED` fields instead of creating brand-new rows
- Experts not selected again keep their prior terminal offer status unchanged
- Experts listed in `previousExpertIds` stay excluded, while the internal expert can be reactivated so fallback remains available

**Success:**
```json
{
  "error": false,
  "message": "Request retry started.",
  "data": { "request": {} }
}
```

**Errors:** `404` request not found or not owned by user, `409` request is no longer retryable

## Refund Handling

There is no mobile-user self-service refund endpoint.

If a user asks for a refund, that request is handled offline outside this app. When an admin approves the case and finishes the store-side refund flow, the admin can restore credits in Coinzy Experts with `POST /admin/users/:userId/credits/adjust`.

## Get Report For Request

### `GET /users/requests/:requestId/report`

Returns only a submitted (non-draft) report for a request owned by the authenticated user. The complete structured evaluation is in `contentFields`; top-level `content` is a retired legacy storage field and is never returned.

The report includes the expert-authored `coinTitle`; the completed Request returned by list/detail endpoints carries the same value.

When a report is submitted, the completed request also exposes `reportId` pointing to that report. Before submission, the request-side `reportId` remains `null`.

`requestDisplayId` is a redundant display snapshot only. Report ownership and lookups continue to use the MongoDB `requestId`; legacy reports may return `requestDisplayId: null`.
